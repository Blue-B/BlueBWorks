# 매 회차 절차

1. 실제 Asia/Seoul 날짜·시간을 확인한다. 예약 오전 회차는 am, 저녁 회차는 pm이다. 현재 실행이 13시 이전이면 am, 이후면 pm으로 해석한다. 재개 요청은 기존 회차 식별자를 보존한다.
2. 저장소 private 여부, main, AGENTS.md, 최근 프로젝트, 모든 상태의 최근 daily PR, 해당 회차 브랜치·보고서를 읽는다. main에 완료된 회차는 중복 생성하지 않는다. PR에만 남아 있으면 기존 변경을 보존해 검증·main 반영부터 끝낸다. 과거 상태 기록을 현재 장애로 단정하지 않는다.
3. 최신 공개 정보로 후보 세 개 이상을 비교한다. 최신 기술 이름을 억지로 넣지 않는다. 제품의 실제 쓰임새와 기존 대안 두 개 이상과의 차이로 하나를 고른다. 공식 출처를 포함해 서로 다른 URL 두 개 이상과 확인일을 기록한다.
4. 독립 실행 가능한 핵심 기능을 실제 구현한다. 사용자 입력, 정상 동작, 잘못된 입력, 빈 상태, 필요한 경우 모바일 레이아웃까지 처리한다. 가짜 연동·허위 수치·데모 전용 데이터만으로 완성했다고 하지 않는다.
5. `projects/<slug>/project.json`을 실제 조사·코드 내용에 맞춰 작성한다. README에는 용도, 설치·실행, 예제, 테스트, 비용·데이터 처리, 한계, 비교와 출처를 포함한다.
6. 저장소 검사와 프로젝트 실제 테스트·필요한 빌드를 실행한다. 실행 환경이 실패하면 승인된 다른 실행 도구·임시 환경·GitHub Actions를 사용한다. 검증한 파일과 반영할 파일이 일치하는지 확인한다. 실행 도구가 없거나 승인 대기로 막히면 그 사실을 보고한다.
7. 회차 브랜치에 실제 push하고 PR을 만든 뒤 검증된 변경을 비공개 main으로 실제 병합한다. 소유자는 이 main 반영까지 승인했다. PR만 남기고 종료하지 않는다. 보호 규칙·필수 검사·리뷰·앱 승인 우회, force-push는 하지 않는다. 실제 테스트·빌드 실패나 미검증 상태면 해결 전 main에 반영하지 않는다. 원격 CI가 테스트 시작 전 막혔을 때의 직접 검증 조건은 AGENTS.md를 따른다.
8. 반영 후 GitHub에서 main 커밋 SHA, `projects/<slug>/` 실제 소스와 보고서를 다시 조회하고 파일이 검증한 내용과 일치함을 확인한다. main에 없으면 반영 미완료로 보고한다. 저장소 기본 화면의 프로젝트 안내도 실제 결과와 맞춘다.
9. 회차 보고서에 선정 근거, 대안 비교, 구현 내용, 직접 검증과 원격 CI의 실제 결과, main 반영 여부, 커밋·PR·검사 링크, 실행 방법과 한계를 기록한다. 아직 모르는 링크는 지어내지 않는다. 코드 커밋을 검증한 뒤 문서에 그 코드 커밋을 인용할 수 있다.
10. 사용자에게 사람이 이해할 수 있는 한국어로 결과와 main 기준 프로젝트 링크·최종 커밋 링크를 보고한다. 미완성·실패·main 미반영은 완료 개수에서 제외한다. 두 개 목표를 맞추려고 저품질 프로젝트를 추가하거나 기존 프로젝트 수정·문서 작업을 신규 프로젝트로 세지 않는다. 수동 성공과 무인 예약 실행 성공은 구분한다.

private을 유지하며 유료 호출·결제·릴리즈·외부 배포·홍보·계정 생성·다른 저장소 변경은 별도 승인 없이는 하지 않는다. 전체 승인 범위와 개인정보 규칙은 AGENTS.md를 따른다.
