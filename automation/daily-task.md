# 매 회차 절차

GitHub Actions는 어떤 단계에서도 사용하지 않는다. 자동·수동 실행, 재실행, 새 workflow 추가나 복원을 하지 않는다. 과거 문서의 Actions 대체 실행 지시는 적용하지 않는다.

1. 실제 Asia/Seoul 날짜·시간을 확인한다. 13시 이전 am, 이후 pm으로 정하며 재개는 기존 회차 식별자를 보존한다.
2. 실행 시작 직후 원격 main SHA, private 여부, AGENTS.md, 최근 프로젝트, 해당 회차 보고서와 작업 브랜치를 읽는다. 완료 회차는 중복 생성하지 않는다. 기존 작업 브랜치나 PR에 미완성 변경이 있으면 버리지 말고 이어서 완성한다.
3. 이번 회차 전용 작업 브랜치를 먼저 만든다. 프로젝트 골격(README, project.json, 최소 실행 소스)이 생기는 즉시 첫 체크포인트 커밋을 원격 브랜치에 올린다. GitHub 반영을 맨 마지막 한 번으로 미루지 않는다.
4. 최신 공개 정보로 후보 세 개 이상을 비교하되 조사에 과도한 시간을 쓰지 않는다. 실제 쓰임새와 기존 대안 두 개 이상과의 차이로 하나를 고른다. 구현 범위는 이번 회차 안에 테스트와 main 반영까지 가능한 크기로 제한한다.
5. 독립 실행 가능한 핵심 기능, 실제 사용자 입력, 잘못된 입력, 빈 상태, 필요한 모바일 화면을 구현한다. 가짜 연동·허위 수치·데모 전용 입력만으로 완성했다고 하지 않는다. 기능 단위가 끝날 때마다 원격 작업 브랜치에 체크포인트를 남긴다.
6. projects/<slug>/project.json과 프로젝트 README를 실제 소스·조사에 맞춰 작성한다. 사용법·예제·검사·비용·데이터 처리·한계·비교·출처를 포함한다. UI 프로젝트는 선명한 PNG와 실제 기능 흐름이 반복되는 demo.gif를 만들고 프로젝트 README와 메인 README에 올바른 상대경로로 넣는다.
7. DevSpace·Oracle 또는 임시 실행 환경에서 저장소 검사, 프로젝트 정상·오류·경계 테스트, 필요한 빌드·화면 검사를 직접 수행한다. 한 실행 경로가 실패하면 승인된 다른 실행 환경을 쓰되 Actions는 사용하지 않는다. DevSpace 장애를 GitHub push 장애로 일반화하지 않는다.
8. 검증 완료 후 reports/YYYY-MM/YYYY-MM-DD-am-auto.md 또는 pm-auto.md를 만들고 첫 부분에 `run_source: scheduled`를 명시한다. 검증한 소스와 반영할 파일이 일치하는지 확인하고 메인 README까지 갱신한 뒤 작업 브랜치에 최종 체크포인트를 올린다.
9. 작업 브랜치를 private main까지 실제 반영한다. PR을 쓴다면 생성으로 끝내지 말고 실제 병합까지 수행한다. 테스트·빌드 실패, 미검증, 충돌, 보호 규칙·필수 리뷰·앱 승인 차단을 무시하지 않는다. 필수 검사가 Actions를 요구해도 Actions를 실행하거나 보호 규칙을 우회하지 않는다.
10. 반영 직후 GitHub에서 원격 main을 다시 조회한다. 최종 main SHA, projects/<slug>/ 실제 파일, 자동 보고서, 메인 README의 프로젝트 항목과 미리보기 경로가 모두 그 main에 존재해야만 회차 성공이다. 하나라도 없으면 완료라고 보고하지 않는다.
11. 시간·도구 제약이 생기면 부가기능을 줄여서라도 테스트 가능한 완제품과 main 반영을 우선한다. 프로젝트 이름, 설명, 실행법, 테스트 결과, 미리보기 경로, 최종 main SHA를 짧게 보고한다. 중요한 실패·제약·미검증은 숨기지 않는다.

private을 유지하며 유료 호출·결제·릴리즈·외부 배포·홍보·계정 생성·다른 저장소 변경은 별도 승인 없이는 하지 않는다. 전체 규칙은 AGENTS.md를 따른다.
