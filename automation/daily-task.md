# 매 회차 절차

GitHub Actions는 어떤 단계에서도 사용하지 않는다. 자동·수동 실행, 재실행, 새 workflow 추가나 복원을 하지 않는다. 과거 문서의 Actions 대체 실행 지시는 적용하지 않는다.

1. 실제 Asia/Seoul 날짜·시간을 확인한다. 13시 이전 am, 이후 pm으로 정하며 재개는 기존 회차 식별자를 보존한다.
2. private 여부, main, AGENTS.md, 최근 프로젝트, 모든 상태의 최근 daily PR, 해당 회차 브랜치·보고서를 읽는다. 완료 회차는 중복 생성하지 않고 PR에만 있으면 기존 변경을 보존해 검증·main 반영부터 끝낸다. 과거 장애를 현재 사실로 단정하지 않는다.
3. 최신 공개 정보로 후보 세 개 이상을 비교한다. 실제 쓰임새와 기존 대안 두 개 이상과의 차이로 하나를 고른다. 공식 출처를 포함해 서로 다른 URL 두 개 이상과 확인일을 기록한다. 기술 이름을 억지로 넣지 않는다.
4. 독립 실행 가능한 핵심 기능, 실제 사용자 입력, 잘못된 입력, 빈 상태, 필요한 모바일 화면을 구현한다. 가짜 연동·허위 수치·데모 전용 입력만으로 완성했다고 하지 않는다.
5. projects/<slug>/project.json과 프로젝트 README를 실제 소스·조사에 맞춰 작성한다. 사용법·예제·검사·비용·데이터 처리·한계·비교·출처를 포함한다. 메인 README에는 프로젝트 이름·짧은 설명·실제 미리보기만 둔다.
6. DevSpace·Oracle 또는 임시 실행 환경에서 저장소 검사, 프로젝트 정상·오류·경계 테스트, 필요한 빌드·화면 검사를 직접 수행한다. 한 실행 경로가 실패하면 승인된 다른 실행 환경을 쓰되 Actions는 사용하지 않는다. 실제 실행이 불가능하면 미검증이라고 보고한다. DevSpace 장애를 GitHub push 장애로 일반화하지 않는다.
7. 검증한 소스와 반영할 파일이 일치하는지, 최종 트리에 .github/workflows의 실행 가능한 .yml/.yaml이 없는지 확인한다. 기존 브랜치 재사용·병합으로 workflow를 되살리지 않는다.
8. 실제 원격 push 후 검증된 변경을 비공개 main까지 반영한다. PR을 쓴다면 실제 병합까지 수행한다. 소유자는 main 반영을 승인했다. 테스트·빌드 실패, 미검증, 충돌, 보호 규칙·필수 리뷰·앱 승인 차단을 무시하지 않는다. 필수 검사가 Actions를 요구해도 실행하거나 보호 규칙을 우회하지 않는다.
9. 반영 후 GitHub에서 main SHA, 실제 프로젝트 소스·보고서를 다시 조회하고 검증한 파일이 일치하는지 확인한다. main에 없으면 반영 미완료다. 상세 검증과 커밋·PR 근거는 보고서에 남긴다.
10. 프로젝트 이름, 설명, 열어볼 파일·실제 미리보기, main 반영 여부를 짧게 보고한다. 중요한 실패·제약·미검증은 숨기지 않는다. 미완성은 완료 개수에서 제외하고 수량을 채우려고 기존 수정·문서·설정을 신규 프로젝트로 세지 않는다. 수동 성공과 무인 예약 성공을 구분한다.

private을 유지하며 유료 호출·결제·릴리즈·외부 배포·홍보·계정 생성·다른 저장소 변경은 별도 승인 없이는 하지 않는다. 전체 규칙은 AGENTS.md를 따른다.
