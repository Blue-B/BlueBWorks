먼저 볼 것

  • REST·GraphQL API에서 Copilot 코드리뷰를 요청할 수 있다.
  • 요청마다 리뷰 effort level을 지정할 수 있고 Balanced가 기본값이 됐다.
  • Copilot Pro·Pro+·Max·Business·Enterprise에서 일반 제공된다.

편집 메모

이번 업데이트의 핵심은 ‘AI가 리뷰를 더 잘한다’가 아니라 호출 지점이 바뀌었다는 데 있다. 리뷰를 CI 이후, 배포 직전, 특정 라벨이 붙은 PR처럼 팀이 정한 운영 규칙 안에 넣을 수 있게 됐다. 코드리뷰를 개발자 개인 기능이 아니라 엔지니어링 시스템의 한 단계로 보는 팀이라면 변화 폭이 크다.

무엇이 달라졌나

GitHub는 10월 2일부터 Copilot code review를 지원되는 REST·GraphQL API에서 직접 요청할 수 있게 했다. 요청 시 리뷰 강도(effort level)를 선택할 수 있고, 기존 저장소와 조직의 기본 리뷰 강도도 Balanced로 변경됐다. 이전에는 PR UI 중심 기능이었다면 이제 코드에서 리뷰 시작 조건을 제어할 수 있다.

실무에서는 어디에 붙일 수 있나

가장 직접적인 활용처는 팀 내부 자동화다. 예를 들어 변경 파일이 일정 규모를 넘거나 보안 관련 디렉터리를 건드렸을 때만 Copilot 리뷰를 추가로 요청하고, 결과를 사람이 보는 필수 리뷰와 병렬로 돌릴 수 있다. 자체 대시보드나 릴리스 도구가 있는 조직이라면 GitHub 화면으로 이동하지 않고 그 도구에서 리뷰를 시작하는 흐름도 만들 수 있다.

Balanced 기본값이 의미하는 것

GitHub는 리뷰 강도의 기본값을 Balanced로 바꿨다. Lite보다 더 깊은 분석을 하되 비용과 지연을 무한정 키우는 방식은 피하려는 기본 선택이다. 다만 상위 조직 설정을 저장소가 재정의할 수 있는 계층 구조이므로, 여러 조직을 운영한다면 단순히 ‘기본값이 바뀌었다’고 끝내지 말고 실제 적용 레벨을 확인하는 편이 안전하다.

도입 전에 볼 점

AI 리뷰는 사람 리뷰를 대체하는 승인 장치로 두기보다, 사람이 놓치기 쉬운 패턴을 먼저 훑는 보조 단계로 설계하는 편이 현실적이다. 특히 자동 호출을 넓히면 리뷰 횟수와 비용도 함께 늘 수 있으므로 변경 규모·위험도·브랜치 정책 같은 조건으로 호출 범위를 좁혀 시작하는 게 좋다.
