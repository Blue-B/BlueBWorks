Copilot Dynamic Workflows란: 에이전트 작업 절차를 프로그램으로 만든다

장애가 나면 할 일은 대체로 정해져 있다. 로그와 지표를 모으고, 시스템별로 원인을 살피고, 결과를 합쳐 타임라인과 원인 보고서를 쓴다. 그런데 에이전트에게 이 일을 맡기면 매번 순서가 달라지고, 어떤 날은 한 시스템을 빠뜨린다. 절차가 재현되지 않으니 결과를 믿기 어렵다.

GitHub는 2026년 10월 1일 Copilot CLI, GitHub Copilot 앱, GitHub Copilot SDK에 Dynamic Workflows를 추가했다. Dynamic workflow는 작업을 어떻게 수행할지 정의한 프로그램이다. 자동화된 단계와 하나 이상의 에이전트 작업을 섞고, 단계는 차례대로, 동시에, 또는 둘을 섞어 실행할 수 있다.

핵심은 무엇을 코드가 정하고 무엇을 에이전트가 맡는지 나누는 것이다. 단계, 에이전트를 언제 부를지, 그 결과를 어떻게 쓸지는 모두 코드로 정하고, 에이전트는 분석이나 판단이 필요한 부분만 맡는다. 위의 장애 조사라면 같은 단계가 매번 같은 순서로 실행된다.

워크플로는 Copilot 확장(extension) 안에 들어 있다. 그래서 Copilot의 확장 API를 그대로 쓸 수 있고, 명령 실행, 도구 사용, 다른 서비스 호출, 하위 에이전트 간 결과 검증, 사용자 입력 요청, 체크포인트에서 멈추기까지 할 수 있다. 에이전트에게 정해진 형식으로 결과를 돌려 달라고 하면 다음 단계가 그 결과를 받아 쓴다.

Autopilot, /fleet과 무엇이 다른가

Copilot에는 이미 여러 에이전트를 쓰는 방법이 있다. 그래서 Dynamic workflow가 같은 기능처럼 보일 수 있는데, GitHub 문서는 차이가 에이전트 수가 아니라 작업을 누가 계획하고 통제하느냐에 있다고 설명한다.

Autopilot은 자율성에 초점을 둔 모드다. Copilot이 단계마다 사용자에게 묻지 않고 다음 단계를 스스로 정하며 계속 일한다. /fleet은 Copilot이 작업을 하위 에이전트에 나눠 맡기고 병렬로 조율하도록 유도하는데, 작업을 어떻게 나눌지는 매번 Copilot이 정한다.

Dynamic workflow는 코드로 정의한 절차를 수행한다. 워크플로 작성자가 단계, 조건, 인계를 정하고, 에이전트는 하나든 여럿이든 그 절차 안에서 차례로 또는 동시에 일한다. 같은 워크플로를 다시 쓰면 같은 단계와 규칙을 다시 쓰는 것이다.

그렇다고 결과가 항상 같지는 않다. 문서는 입력이나 중간 결과에 따라 단계 사이의 경로가 달라질 수 있고, 에이전트의 답도 실행마다 다를 수 있다고 분명히 적었다. 고정되는 것은 절차이지 결론이 아니다.

Dynamic Workflows 켜는 법과 첫 워크플로 만들기

GitHub Copilot 앱에서는 따로 설정할 것 없이 항상 쓸 수 있다. Copilot CLI에서는 최신 버전에서 실험 기능을 켜야 한다. CLI를 --experimental 옵션으로 실행하거나, 대화형 세션에서 /experimental on을 입력한다. CLI 업데이트는 /update로 한다.

워크플로는 직접 쓰지 않아도 된다. 자주 하는 작업을 설명하며 Copilot에게 워크플로를 만들어 달라고 하면 된다. 기본으로는 현재 세션용 확장으로 만들어지고, 개인 확장이나 프로젝트 확장으로 만들어 달라고 할 수도 있다. 직접 쓰고 싶다면 Copilot에 들어 있는 작성 안내를 참고한다.

실행도 자연어로 한다. 'java-security-review 워크플로를 현재 디렉터리의 java 파일에 실행해 줘'처럼 이름으로 부르면 Copilot이 백그라운드에서 돌리고 끝나면 알려 준다. 그동안 세션에서 다른 일을 계속할 수 있다. 어떤 워크플로가 있는지는 'What dynamic workflows are available?'이라고 물으면 된다.

CLI에서는 대화 없이 copilot workflow run 명령으로 바로 실행할 수도 있다. 이 명령은 실행이 끝나거나 멈출 때까지 기다렸다가 셸로 돌아오므로, 스크립트나 CI/CD 파이프라인에서 같은 입력으로 반복 실행하고 결과를 저장하는 데 쓸 수 있다. 다만 이 방식은 권한 승인 창을 띄우지 않으니 필요한 권한을 미리 줘야 한다.

실행 중인 워크플로는 CLI의 /workflows 명령이나 앱의 Workflows 버튼으로 본다. 사용한 AI 크레딧, 단계, 진행 메시지, 하위 에이전트가 표시되고 여기서 취소하거나 일시 중지할 수 있다. 멈춘 실행을 다시 고르면 완료된 단계의 저장된 결과를 재사용해 이어 간다. 확장에 따라서는 슬래시 명령, 사용자 도구, 훅, 앱의 캔버스 화면으로 워크플로를 시작하게 만들 수도 있다.

어떤 작업에 쓰면 좋은가: GitHub가 든 예

GitHub는 재사용할 절차를 정하고 싶을 때, 또는 한 작업에 분명한 단계와 점검, 제한이 필요할 때 Dynamic workflow를 쓰라고 권한다. 릴리스 점검을 돌리고 한 에이전트가 실패를 평가하게 한 뒤, 사용자가 결과를 검토할 때까지 멈췄다가 재개하는 흐름이 대표적인 예다.

병렬 처리가 잘 맞는 일도 있다. 풀 리퀘스트의 변경 파일이 많을 때 파일별로 동시에 리뷰하거나, 큰 코드베이스에서 테스트가 빠진 곳이나 없앨 API를 쓰는 곳을 여러 디렉터리에 걸쳐 한꺼번에 찾는 일이다.

검증을 코드로 거는 예도 있다. 병합된 풀 리퀘스트에서 해결되지 않은 리뷰 코멘트를 코드로 찾고, 두 모델에게 그 코멘트가 아직 유효한지 묻고, 두 모델이 동의할 때만 보고하게 하는 식이다. 한 모델의 판단을 그대로 믿지 않는 장치를 절차에 넣을 수 있다.

반대로 빠른 답이나 간단한 수정은 일반 채팅 모드의 평범한 프롬프트로 충분하다고 GitHub는 적었다. 절차를 코드로 만드는 비용이 있으니 반복하거나 단계가 많은 일에만 쓰는 편이 맞다.

GitHub Changelog와 Docs가 든 활용 예를 정리했다. 간단한 질문이나 작은 수정에는 일반 채팅이 권장된다.

권한과 비용 제한: 하위 에이전트 수와 AI 크레딧 상한 걸기

워크플로의 하위 에이전트는 CLI 권한 체계를 쓰고, 워크플로를 시작한 세션의 권한을 물려받는다. 세션에서 이미 허용한 것은 하위 에이전트에도 적용된다. 허용되지 않은 동작을 하려 하면 대화형 CLI 세션에 일반 권한 요청으로 뜨고, 해당 하위 에이전트는 답할 때까지 기다린다. 한 번 세션 동안 허용하면 같은 권한이 필요한 모든 하위 에이전트에 적용된다.

비용 관리는 제한으로 한다. 동시에 활동하는 하위 에이전트 수, 실행 전체에서 띄울 수 있는 하위 에이전트 총수, 멈춘 시간을 뺀 활성 실행 시간, 그리고 에이전트와 하위 에이전트가 쓸 수 있는 AI 크레딧의 대략적 상한, 이렇게 네 가지다.

제한은 세 곳에서 정할 수 있다. 실행할 때 프롬프트에 자연어로 적는 것, 워크플로 코드에 넣어 두는 것, 개인 설정에 기본값으로 두는 것이다. 같은 종류의 제한이면 프롬프트가 코드보다, 코드가 개인 설정보다 우선한다. CLI에서는 /settings로 workflows.defaultLimits.maxConcurrentSubagents, maxTotalSubagents, timeoutSeconds, maxAiCredits를 정한다.

동시 실행 제한에 걸리면 추가 하위 에이전트는 기다릴 뿐 워크플로가 멈추지 않는다. 나머지 제한에 걸리면 실행이 멈추지만 상태와 저장된 결과는 남아 나중에 재개할 수 있다. 재개할 때 늘리는 제한은 멈추기 전 사용량을 포함한 실행 전체 합계라는 점에 주의한다. GitHub는 큰 작업 전에 작은 범위로 먼저 돌려 실제 AI 크레딧 사용량을 보고 상한을 정하라고 권한다.

공유와 수정, 요금제 조건

Copilot이 만들어 준 워크플로는 기본적으로 현재 세션 범위다. 세션을 넘어 쓰려면 확장을 개인 확장 디렉터리로, 프로젝트 사람들과 공유하려면 저장소의 확장 디렉터리로 복사한다. 공유되는 것은 정의뿐이고, 원래 세션의 실행 기록이나 저장된 진행 상황은 따라가지 않는다. 더 넓게 배포하려면 플러그인으로 묶을 수 있다.

처음에는 범위를 좁혀 시험하라고 문서는 권한다. 여러 파일을 처리하는 워크플로라면 두세 개 파일로 먼저 돌려 보고, 고칠 점은 자연어로 요청해 저장된 정의 자체를 바꾼다. 저장소에서 공유한 워크플로를 고치면 다른 사람은 저장소를 받아 확장을 다시 불러와야 새 판을 쓴다.

요금제 조건은 발표 이후 문서에서 더 구체적으로 적혔다. 발표 당시 Changelog는 모든 Copilot 요금제에서 쓸 수 있다고 했고, 10월 29일 확인한 GitHub Docs는 기존 연간 요금제에 남아 예전의 프리미엄 요청 기반 과금을 쓰는 Copilot Pro·Pro+ 구독자는 제외된다고 적고 있다. 연간 요금제 사용자는 자신의 과금 방식을 먼저 확인하는 편이 좋다.

Dynamic Workflows는 어떻게 켜나요?

GitHub Copilot 앱에서는 설정 없이 쓸 수 있습니다. Copilot CLI에서는 최신 버전을 --experimental 옵션으로 실행하거나 세션에서 /experimental on을 입력합니다.

/fleet과 무엇이 다른가요?

/fleet은 Copilot이 매번 작업을 나눠 하위 에이전트에 맡깁니다. Dynamic workflow는 작성자가 코드로 단계, 조건, 인계를 정해 같은 절차를 반복 실행합니다.

동시·총 하위 에이전트 수, 실행 시간, AI 크레딧 상한을 프롬프트, 워크플로 코드, 개인 설정에서 걸 수 있습니다. 큰 작업 전에 작은 범위로 시험해 실제 사용량을 보고 상한을 정하는 것이 권장됩니다.

모든 Copilot 요금제에서 쓸 수 있나요?

발표 당시에는 모든 요금제라고 했지만, 현재 GitHub Docs는 레거시 프리미엄 요청 과금을 쓰는 기존 연간 Copilot Pro·Pro+ 구독자를 제외한다고 적고 있습니다.
