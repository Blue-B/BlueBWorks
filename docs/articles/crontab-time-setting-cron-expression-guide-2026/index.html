크론탭 시간 설정, 크론 표현식 읽는 법과 자주 틀리는 곳

크론탭 시간 설정은 분, 시, 일, 월, 요일 다섯 칸만 알면 읽힙니다. 다만 */35 가 35분마다가 아니라는 점, 날짜와 요일을 같이 적으면 둘 중 하나만 맞아도 돈다는 점, 서버 시간대와 GitHub Actions 의 UTC 기준처럼 표현식만 봐서는 모르는 함정이 있습니다. 자주 쓰는 예시와 함께 정리했습니다.

요약
  • 다섯 칸은 왼쪽부터 분, 시, 일, 월, 요일입니다. 5분마다는 */5 * * * *, 매일 새벽 3시는 0 3 * * *, 평일 오전 9시는 0 9 * * 1-5 입니다.
  • */35 는 35분 간격이 아니라 매시 0분과 35분에 돕니다. 나누기는 그 칸 안에서만 계산됩니다.
  • 일 칸과 요일 칸을 둘 다 숫자로 채우면 둘 중 하나만 맞아도 실행됩니다. 0 9 1 * 1 은 매달 1일과 매주 월요일 두 경우에 모두 돕니다.
  • Ubuntu 기본 cron 은 사용자별 시간대를 지원하지 않습니다. GitHub Actions 는 기본이 UTC 라 한국 시간 자정은 0 15 * * * 로 적습니다.
  • crontab -n 파일이름 으로 설치 전에 문법만 볼 수 있습니다. 여섯 칸짜리 표현식이나 마지막 줄바꿈 누락도 여기서 걸립니다.

크론탭 시간 설정은 다섯 칸만 읽으면 됩니다

서버에서 백업이나 정리 스크립트를 정해진 시각에 돌리려면 대부분 cron 을 씁니다. crontab -e 로 연 파일에 한 줄씩 적는데, 맨 앞 다섯 칸이 시각이고 그 뒤가 실행할 명령입니다.

자주 쓰는 표현식 다섯 개를 crontab.guru 에 넣고 다음 실행 시각 목록을 펼쳐 봤습니다. */5 * * * * 는 10:20, 10:25, 10:30 처럼 5분 간격으로 나왔고, 0 3 * * * 는 다음 날 새벽 3시 정각 하나만 잡혔습니다.

예상과 다르게 나온 것도 두 개 있었습니다. */35 * * * * 는 10:35 다음이 11:10 이 아니라 11:00 이었고, 0 9 1 * 1 은 11월 30일 월요일과 12월 1일에 연달아 잡혔습니다. 둘 다 cron 문서에 적힌 규칙대로 움직인 결과입니다.

칸 순서는 왼쪽부터 분(0~59), 시(0~23), 일(1~31), 월(1~12), 요일(0~7)입니다. 요일은 0 과 7 이 모두 일요일이고, 월과 요일은 jan, mon 처럼 영어 앞 세 글자로 써도 됩니다.1,2,6

자주 쓰는 크론 표현식 예시

별표는 그 칸의 처음부터 끝까지 전부라는 뜻입니다. 쉼표는 목록, 하이픈은 범위, 슬래시는 간격입니다. 이 네 가지만 섞으면 대부분의 일정을 적을 수 있습니다.

평일 오전 9시는 0 9 * * 1-5 입니다. crontab.guru 에 넣으면 금요일인 11월 27일 다음이 바로 11월 30일 월요일이라 주말 이틀을 건너뛰는 것이 목록에서 보입니다.

매일 한 번 도는 작업이라면 0 0 * * * 대신 @daily 처럼 줄여 쓰는 이름도 있습니다. @hourly, @weekly, @monthly, @reboot 도 같은 방식이고, @reboot 는 재부팅 뒤 한 번 돕니다.

분 칸을 비워 두지 않는 것도 중요합니다. 0 9 * * * 대신 * 9 * * * 라고 적으면 9시 정각 한 번이 아니라 9시 0분부터 59분까지 60번을 돕니다.1,2,6

저장 전에 crontab -n 으로 문법 오류 찾기

Ubuntu 와 Debian 의 crontab 에는 -n 옵션이 있습니다. 파일을 넘기면 문법만 보고 실제 crontab 에는 아무것도 쓰지 않습니다. 지금 돌고 있는 일정을 건드리지 않고 오타부터 잡을 수 있습니다.

Ubuntu 24.04 에서 시험용 파일 다섯 개를 만들어 crontab -n 에 넣어 봤습니다. 정상 파일은 The syntax of the crontab file was successfully checked 한 줄과 함께 종료 코드 0 으로 끝났습니다.

시 칸에 25 를 넣은 파일은 bad hour 로 막혔습니다. Spring 식 L 을 일 칸에 넣은 파일은 bad day-of-month 였고, 여섯 칸짜리 0 0 3 * * * 는 여섯째 별표가 명령 자리로 밀리면서 bad command 가 나왔습니다.

마지막 줄 뒤에 줄바꿈이 없는 파일도 missing newline before EOF 오류와 함께 설치를 거부했습니다. 편집기에서 마지막 줄 끝에 엔터를 한 번 넣어 두면 됩니다.

crontab -r 은 지금 crontab 전체를 지우는 옵션입니다. 키보드에서 e 와 r 이 붙어 있어 -e 를 치려다 실수하기 쉬운데, -i 를 같이 주면 지우기 전에 y 를 한 번 묻습니다.5

*/35 는 35분마다가 아닙니다

35분 간격으로 돌리려고 */35 * * * * 를 적으면 실제로는 매시 0분과 35분에 돕니다. crontab.guru 목록도 10:35, 11:00, 11:35, 12:00 으로 나와서 간격이 35분과 25분을 번갈아 갑니다.

슬래시 간격은 그 칸 안에서만 계산되기 때문입니다. 분 칸은 0 부터 59 까지라 0, 35 두 값만 남고, 시가 바뀌면 다시 0 부터 셉니다. cronie 의 crontab 문서도 */35 가 한 시간에 두 번 돈다고 적고 있습니다.

60 을 나누어떨어지게 하는 값(5, 10, 15, 20, 30)은 이런 문제가 없습니다. 시 칸도 같아서 */5 는 0, 5, 10, 15, 20시에 돌고 20시 다음은 25시가 아니라 다음 날 0시입니다.

정말 35분이나 90분 간격이 필요하면 매분 돌리면서 스크립트 안에서 시각을 나눠 보는 방법이 문서에 예시로 나옵니다. 간격이 길다면 시간을 직접 나열하는 쪽이 읽기 쉽습니다.2,6

날짜와 요일을 둘 다 적으면 둘 중 하나만 맞아도 돕니다

매달 1일이 월요일일 때만 돌리고 싶어서 0 9 1 * 1 이라고 쓰는 경우가 있습니다. 이 표현식은 1일에도, 매주 월요일에도 돕니다. crontab.guru 설명도 day-of-month 1 and on Monday 로 나옵니다.

실행 목록을 펼치면 11월 30일 월요일, 12월 1일 화요일, 12월 7일 월요일 순서였습니다. 1일과 월요일이 겹치는 날만 고르는 것이 아니라 두 조건을 합친 것입니다.

Debian 과 Ubuntu 의 crontab 문서도 일과 요일 두 칸이 모두 별표가 아니면 둘 중 하나만 맞아도 실행한다고 적고 있습니다. 문서 예시인 30 4 1,15 * 5 는 매달 1일과 15일, 그리고 매주 금요일에 돕니다.

둘 다 맞을 때만 돌리려면 한쪽 조건은 명령 안에서 거르는 방법이 흔합니다. 예를 들어 0 9 1 * * 로 매달 1일에 돌리고, 명령 앞에 오늘이 월요일인지 보는 조건을 붙입니다.1,2,6

크론탭 시간대는 서버 시간을 따릅니다

cron 은 그 서버의 시간대로 표현식을 읽습니다. 해외 리전에 만든 클라우드 서버는 UTC 로 설정된 경우가 많아서, 0 3 * * * 가 한국 시간 새벽 3시가 아니라 낮 12시에 돌 수 있습니다.

먼저 date 명령으로 서버 시간대를 봅니다. Ubuntu 24.04 WSL 에서 date 는 10:21 KST 를, TZ=UTC date 는 01:21 UTC 를 보여 줬습니다. 끝에 붙은 KST 나 UTC 가 cron 이 따르는 기준입니다.

Ubuntu 와 Debian 에 기본으로 들어 있는 cron 은 사용자별 시간대를 지원하지 않습니다. crontab 맨 위에 TZ=UTC 를 적어도 실행되는 명령의 환경만 바뀌고, 언제 돌지는 여전히 서버 시간대로 정해진다고 문서에 나와 있습니다.

Fedora 나 RHEL 계열에서 쓰는 cronie 는 CRON_TZ 변수로 그 파일의 시간대를 따로 정할 수 있습니다. 같은 crontab 을 다른 배포판으로 옮길 때 이 차이 때문에 시각이 어긋날 수 있습니다.1,2

GitHub Actions cron 은 UTC 기준입니다

GitHub Actions 의 schedule 도 같은 다섯 칸 문법을 쓰지만 기본 시간대가 UTC 입니다. 한국 시간은 UTC 보다 9시간 빠르니 한국 시간 기준으로 원하는 시각에서 9시간을 빼서 적어야 합니다.

한국 시간 자정에 돌리려면 0 15 * * * 입니다. date 명령으로 UTC 15시를 한국 시간으로 바꾸자 다음 날 00:00 KST 가 나왔고, 반대로 한국 시간 오전 9시는 UTC 0시였습니다.

날짜가 하루 밀린다는 점도 같이 봐야 합니다. 한국 시간 월요일 오전 8시는 UTC 로 일요일 23시라 요일 칸이 0 이 됩니다. 평일만 돌리는 작업은 요일 범위까지 같이 옮겨야 합니다.

GitHub 문서에는 cron 아래에 timezone 으로 IANA 시간대 이름을 적는 방법도 나와 있습니다. Asia/Seoul 을 적으면 한국 시간 그대로 써도 됩니다. 가장 짧은 실행 간격은 5분에 한 번입니다.3,6

크론 표현식 6자리는 초가 맨 앞에 붙은 형식

크론 표현식이 여섯 칸이면 Spring 이나 Quartz 같은 자바 스케줄러용일 가능성이 큽니다. Spring 문서 기준으로 맨 앞이 초이고, 그 뒤가 분, 시, 일, 월, 요일입니다.

그래서 같은 의미라도 칸 수가 다릅니다. 매일 새벽 3시는 crontab 에서 0 3 * * * 이고 Spring 에서는 0 0 3 * * * 입니다. 여섯 칸짜리를 crontab 에 넣으면 앞에서 본 것처럼 bad command 로 막힙니다.

Spring 형식에는 crontab 에 없는 기호도 있습니다. L 은 그달 마지막 날, 1W 는 그달 첫 평일, MON#1 은 첫째 월요일입니다. 리눅스 기본 cron 은 이 기호를 모르니 옮겨 쓸 때 빼야 합니다.4

명령 칸에서 자주 막히는 % 와 환경 변수

시각을 맞게 적었는데 명령이 안 도는 경우는 명령 칸 문제일 때가 많습니다. 대표적인 것이 % 기호입니다. crontab 명령 안의 % 는 줄바꿈으로 바뀌어서 date +%F 같은 명령이 중간에 잘립니다.

날짜를 파일 이름에 넣으려면 \% 처럼 역슬래시를 붙입니다. 위의 월요일 조건 예시에서 \%u 로 쓴 것도 같은 이유입니다.

cron 은 로그인 셸과 다른 환경에서 돕니다. 기본 셸은 sh 이고 계정 정보에서 채워지는 변수는 HOME 과 LOGNAME 정도라, 터미널에서 잘 되던 명령이 경로를 못 찾을 수 있습니다. 명령은 전체 경로로 적는 편이 안전합니다.

출력을 파일로 남겨 두면 원인을 찾기 쉽습니다. 명령 끝에 >> $HOME/cron.log 2>&1 을 붙이면 성공한 출력과 오류가 모두 한 파일에 쌓입니다. 지금 등록된 목록은 crontab -l 로 볼 수 있습니다.1,2
