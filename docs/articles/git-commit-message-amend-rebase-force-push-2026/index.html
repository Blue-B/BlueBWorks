git 커밋 메시지 수정, 마지막 커밋과 이전 커밋 그리고 push 한 뒤

git 커밋 메시지를 고치는 세 가지 경우를 연습 저장소에서 직접 해 보고 정리했습니다. 마지막 커밋은 commit --amend, 이전 커밋은 rebase -i 의 reword, 이미 push 했다면 --force-with-lease 와 --force-if-includes 를 함께 씁니다.

요약
  • 아직 push 하지 않았다면 마지막 커밋은 git commit --amend, 그보다 앞의 커밋은 git rebase -i 에서 pick 을 reword 로 바꾸면 됩니다. 어느 쪽이든 커밋 해시가 새로 만들어집니다.
  • 이미 push 한 커밋을 고쳤다면 일반 push 는 거절됩니다. --force 대신 --force-with-lease --force-if-includes 를 함께 써야 그사이 올라온 동료 커밋을 덮어쓰지 않습니다.

git 커밋 메시지 수정, push 했는지부터 봅니다

커밋 메시지에 오타를 내거나 이슈 번호를 빠뜨리는 일은 생각보다 자주 생깁니다. 고치는 명령은 두 개뿐인데, 그 커밋을 이미 원격 저장소에 올렸는지에 따라 뒷정리가 완전히 달라집니다.

직접 확인해 보려고 WSL 우분투의 git 2.43.0 으로 연습 저장소를 만들고, 원격 역할을 할 빈 저장소(bare)를 옆에 하나 더 두었습니다. 로그인 버그 수졍이라고 오타를 낸 커밋 e06f419 에 git commit --amend 를 실행하자 메시지가 로그인 버그 수정으로 바뀌면서 해시가 dee6d31 로 달라졌습니다.

이전 커밋 세 개를 rebase -i 로 고쳤을 때는 메시지를 바꾼 건 맨 아래 하나뿐인데도 위의 두 커밋까지 해시가 모두 바뀌었습니다. 그 상태로 push 하자 non-fast-forward 로 거절됐고, 동료 역할 저장소에서 커밋을 하나 올린 뒤에는 강제 푸시 방식에 따라 그 커밋이 지워지기도 하고 막히기도 했습니다.

정리하면 순서는 이렇습니다. 아직 push 하지 않은 커밋이면 마음 편히 고치면 되고, 이미 push 한 커밋이면 혼자 쓰는 브랜치인지부터 봅니다. 여럿이 같이 쓰는 main 이나 develop 브랜치라면 메시지 오타 정도는 그대로 두는 편이 대부분 낫습니다.1,2

마지막 커밋 메시지는 commit --amend

가장 최근 커밋 하나만 고칠 때는 git commit --amend 를 씁니다. 그냥 실행하면 기존 메시지가 들어 있는 편집기가 열리고, 저장하고 닫으면 끝납니다. 편집기를 거치지 않으려면 -m 뒤에 새 메시지를 바로 적습니다.

아래가 연습 저장소에서 실제로 나온 결과입니다. amend 전에는 맨 위 커밋이 e06f419 였는데, 실행 직후 같은 자리에 dee6d31 이 들어섰습니다. 메시지만 바꿨어도 git 입장에서는 새 커밋을 하나 만들어 갈아 끼운 것입니다.

출력에 찍힌 Date 는 처음 커밋했던 시각 그대로입니다. amend 는 작성자와 작성 시각을 기본으로 유지하고, 커밋한 사람 정보만 지금 시각으로 바꿉니다. 작성 시각까지 새로 찍고 싶다면 --reset-author 를 붙입니다.

메시지가 아니라 파일을 빠뜨렸을 때도 같은 명령을 씁니다. 빠진 파일을 git add 로 올린 뒤 git commit --amend --no-edit 를 실행하면 메시지는 그대로 두고 그 파일만 마지막 커밋에 합쳐집니다.

amend 는 언제나 맨 위 커밋 하나에만 작동합니다. 고치려는 커밋 위에 다른 커밋이 이미 쌓여 있다면 amend 로는 손댈 수 없으니 다음에 나오는 rebase 방법으로 넘어갑니다.1,4

이전 커밋 메시지는 rebase -i 에서 reword

두세 개 전 커밋 메시지를 고칠 때는 대화형 리베이스를 씁니다. 최근 세 개 안에 있다면 git rebase -i HEAD~3 을 실행합니다. 편집기에 오래된 커밋부터 pick 줄이 나열되는데, 고칠 커밋 앞의 pick 을 reword(줄여서 r)로 바꾸고 저장합니다.

그러면 reword 로 표시한 커밋마다 메시지 편집기가 차례로 한 번씩 열립니다. 새 메시지를 쓰고 저장하면 다음 커밋으로 넘어가고, 마지막에 Successfully rebased 가 나오면 끝입니다. 줄 순서를 바꾸거나 지우면 커밋 순서가 바뀌거나 커밋이 사라지니 pick 이라는 낱말만 고칩니다.

연습 저장소에서는 세 커밋 중 맨 아래 하나만 reword 로 바꿨습니다. 결과를 보면 메시지를 고친 커밋뿐 아니라 그 위에 쌓인 설정 파일 추가와 README 수정 커밋까지 해시가 전부 바뀌었습니다. 커밋 해시에는 부모 커밋 정보가 들어가기 때문에 아래 커밋 하나가 바뀌면 위쪽이 모두 새로 만들어집니다.

맨 처음 커밋까지 고쳐야 한다면 HEAD~n 대신 git rebase -i --root 를 씁니다. 중간에 꼬였다면 git rebase --abort 로 시작 전 상태로 돌아갈 수 있으니, 리베이스가 끝나기 전에는 겁먹고 다른 명령을 섞지 않는 편이 좋습니다.1,3

push 한 커밋을 고치면 일반 push 가 거절되는 이유

앞의 세 커밋은 이미 원격에 올린 상태였습니다. 리베이스가 끝난 뒤 git status 는 ahead 3, behind 3 을 보여 줬습니다. 내 쪽에는 새 해시 커밋 세 개가 있고, 원격에는 옛 해시 커밋 세 개가 그대로 남아 있다는 뜻입니다.

이 상태에서 그냥 git push 를 하면 non-fast-forward 로 거절됩니다. 원격 기록 위에 이어 붙이는 것이 아니라 원격 기록을 바꿔치기하는 것이라 git 이 막는 것입니다. 안내 문구는 git pull 을 먼저 하라고 하지만, 메시지를 고친 경우에는 따라 하면 안 됩니다. 옛 커밋과 새 커밋이 합쳐져 같은 내용이 두 번 들어간 기록이 생깁니다.

혼자 쓰는 기능 브랜치라면 강제 푸시로 원격 기록을 내 것으로 바꾸면 됩니다. 이때 --force 보다 --force-with-lease 를 씁니다. GitHub 문서도 수정한 커밋을 올릴 때 git push --force-with-lease origin 브랜치 이름 형태를 안내합니다.

--force-with-lease 는 내가 마지막으로 받아 온 원격 상태와 지금 원격 상태가 같을 때만 덮어씁니다. 연습 저장소에서 동료 역할 저장소가 커밋을 하나 올린 뒤 바로 --force-with-lease 로 push 하자 stale info 라는 이유로 거절됐습니다. 그냥 --force 였다면 동료 커밋이 소리 없이 사라졌을 상황입니다.1,2

fetch 뒤의 force-with-lease 는 동료 커밋을 지웠습니다

여기서 많이 하는 실수가 하나 있습니다. 거절 메시지를 보고 git fetch 로 원격 상태를 받아 온 뒤 같은 명령을 다시 실행하는 것입니다. 연습 저장소에서 그대로 해 보니 이번에는 forced update 로 통과했고, 원격 로그에서 동료 커밋이 사라졌습니다.

fetch 를 하면 내 저장소가 기억하는 원격 상태(origin/main)가 최신으로 바뀝니다. --force-with-lease 는 그 기억과 실제 원격만 비교하니, 동료 커밋을 내 브랜치에 합치지 않았어도 둘이 같다고 보고 덮어씁니다. 일부 편집기나 도구가 백그라운드에서 자동으로 fetch 하는 경우에도 같은 일이 생길 수 있습니다.

이걸 막는 옵션이 --force-if-includes 입니다. git 2.30 에 들어온 옵션으로, 원격의 최신 커밋이 내 로컬 브랜치 기록(reflog)에 한 번이라도 들어온 적이 있을 때만 강제 푸시를 허락합니다. 같은 상황에서 두 옵션을 함께 주자 remote ref updated since checkout 이유로 거절됐습니다.

그래서 강제 푸시는 git push --force-with-lease --force-if-includes 로 외워 두는 편이 안전합니다. 매번 치기 번거로우면 git config --global push.useForceIfIncludes true 를 한 번 설정해 두면 --force-with-lease 를 쓸 때 자동으로 함께 적용됩니다.

거절됐다면 동료 커밋을 먼저 내 브랜치에 반영해야 합니다. 동료가 올린 커밋이 내가 고친 커밋들 위에 쌓여 있다면 메시지를 고치려면 동료 커밋까지 다시 써야 하므로, 그때는 메시지 수정을 포기하고 원격 기록을 그대로 받아들이는 쪽이 맞습니다.2

메시지만 고친 커밋이 pull --rebase 에서 사라진 일

마지막으로 하나 더 해 봤습니다. 이미 올라간 README 수정 커밋의 메시지를 amend 로 README 수정 (설치 순서 추가)로 바꾼 뒤, 강제 푸시가 거절되자 git pull --rebase 로 동료 커밋을 받아 왔습니다.

리베이스는 성공했다고 나왔는데 로그를 보니 내가 고친 메시지가 없었습니다. 원격의 옛 커밋 README 수정 위에 동료 커밋만 올라가 있었습니다. 출력 중간에 skippedCherryPicks 안내가 지나갔는데, 바뀐 내용이 이미 원격에 있는 커밋과 똑같아서 내 커밋을 건너뛰었다는 뜻입니다.

git 은 같은 변경인지를 파일 내용으로 판단하고 메시지는 보지 않습니다. 메시지만 고친 커밋은 이렇게 조용히 빠질 수 있으니, pull --rebase 뒤에는 git log --oneline 으로 고친 메시지가 남았는지 한 번 봐야 합니다. 이 경우 git push 결과도 Everything up-to-date 였습니다.

비밀번호나 토큰처럼 지워야 할 정보가 메시지에 들어간 경우라면 강제 푸시만으로 끝나지 않을 수 있습니다. GitHub 문서는 강제 푸시 뒤에도 원래 커밋이 GitHub 에 남을 수 있다며, 옛 커밋 ID 를 적어 GitHub 지원 포털에 삭제를 요청하라고 안내합니다. 노출된 토큰은 메시지를 고치기 전에 먼저 폐기하고 새로 발급하는 것이 순서입니다.1,3
