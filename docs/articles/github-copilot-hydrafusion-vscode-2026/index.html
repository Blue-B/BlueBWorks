덧붙임

HydraFusion은 모델 이름이 아니라 실행 방식을 고르는 기능이라 모델 선택기에 같이 놓여 있어도 비교 기준이 다르다. 그래서 세 실행 방식이 언제 비용을 줄이고 언제 늘리는지, GitHub 벤치마크가 무엇을 쟀는지를 중심으로 정리했다.

HydraFusion은 무엇인가: 모델 하나가 아니라 실행 방식을 고른다

Copilot에서 모델을 고를 때마다 고민이 생긴다. 비싼 모델은 결과가 좋지만 간단한 작업에도 비용이 들고, 싼 모델은 어려운 작업에서 실패한다. 경험 많은 개발자는 이미 손으로 이 문제를 푼다. 쉬운 일은 가벼운 모델에 맡기고, 결과가 미덥지 않으면 다른 모델에게 검토를 시키거나 더 강한 모델로 다시 돌린다.

GitHub의 HydraFusion은 이 과정을 런타임이 대신하게 한 기능이다. 모델 선택기에 HydraFusion이 하나의 항목으로 나타나지만, 실제로는 하나의 모델이 아니라 여러 공급사의 모델을 조합하는 오케스트레이터다. GitHub는 작업 흐름 선택을 최적화 문제로 다룬다고 설명한다. 추론, 코드 생성, 디버깅, 도구 사용에 대한 능력 신호를 보고 품질 기준을 맞추는 가장 효율적인 실행 방식을 고른다는 것이다.

HydraFusion은 원래 Copilot CLI에서 연구 프리뷰로 시험하던 기능이다. 2026년 9월 30일 GitHub Changelog는 이 연구 프리뷰를 Visual Studio Code와 GitHub Copilot 앱으로 넓힌다고 발표했다. 초기 피드백에서 가장 많이 나온 요청이 더 많은 곳에서 쓰게 해 달라는 것이었다고 한다.

이번 판에서는 화면 표시도 손봤다. 워크플로의 각 단계에서 HydraFusion이 무엇을 하는지 더 잘 보이게 했고, 진행 상황을 더 자주 보내 긴 작업에서도 여전히 일하고 있는지 알 수 있게 했다. 여러 모델이 순서대로 돌면 응답이 늦어질 수 있어 이 표시가 실제 사용에서 중요하다.

Single, Cascade, Critique: 세 가지 실행 방식의 차이

Single은 선택된 모델 하나가 작업을 바로 푸는 방식이다. 한 번에 풀 수 있는 작업이라면 다른 모델을 부를 이유가 없으니, 속도와 비용을 아끼는 기본 경로다.

Cascade는 효율적인 모델이 먼저 초안을 만들고, 품질 관문이 그 결과를 받아들일지 더 강한 모델로 올릴지 정한다. 첫 시도는 싸게 하고, 결과가 기준을 넘지 못할 때만 비싼 추론을 쓰는 구조다. 대부분의 작업이 쉬운 쪽에 몰려 있다면 비용이 크게 줄어든다.

Critique는 한 모델이 초안을 만들면 다른 모델 계열의 독립된 읽기 전용 비평자가 검토하고, 초안을 만든 모델이 한 번 고친다. GitHub는 이것이 Copilot CLI의 Rubber Duck 기능과 같은 검토 방식이라고 설명한다. 같은 모델에게 다시 시키는 것보다 다른 관점의 검토가 더 도움이 되는 작업을 위한 경로다.

GitHub 연구 글에 따르면 HydraFusion은 요청마다 필요를 채울 것으로 예상되는 가장 단순한 방식을 고르고, 추가 모델 호출은 결과가 좋아질 가능성이 있을 때만 쓴다. 검토 단계는 도구가 없는 격리된 환경에서 돌아 저장소를 바꾸지 않고, 작업이 취소되거나 검증에 실패하면 패치를 적용하지 않는다고 한다.

연구 글은 이를 다섯 가지 운영 원칙으로 정리했다. 초안·비평·수정·승격·재시도·대체 호출의 비용과 사용량을 빠짐없이 합산하고, 단계마다 시간 제한과 취소 동작을 두며, 검토는 격리하고, 실패하면 적용하지 않고, 실행 전에 워크플로 정의와 모델 연결, 대체 경로, 모델 가용 여부를 검증한다는 것이다. 개발자는 여러 모델이 돌아도 하나의 응답과 하나의 변경 묶음을 받는다.

VS Code와 Copilot 앱에서 HydraFusion 켜는 법

VS Code에서는 1.140 이상이나 VS Code Insiders가 필요하다. Copilot Chat의 모델 선택기에서 HydraFusion을 고르면 된다. 목록에 보이지 않으면 설정에서 chat.copilot.hydraFusion.enabled를 켠다.

GitHub Copilot 앱에서는 먼저 최신 버전으로 업데이트한 뒤 설정에서 HydraFusion을 검색해 켜고, 모델 선택기에서 HydraFusion을 고른다. CLI에서 이미 써 본 사람이라면 같은 기능이 편집기와 앱으로 들어온 것으로 이해하면 된다.

회사 계정이라면 한 단계가 더 있다. HydraFusion은 Copilot Pro, Pro+, Business, Enterprise 사용자가 쓸 수 있는데, Business와 Enterprise는 관리자가 조직이나 엔터프라이즈 설정에서 프리뷰 기능을 허용해야 한다. 개인 설정을 다 켰는데도 목록에 없다면 관리자 정책부터 확인한다.

GitHub 연구 글은 처음 써 볼 작업으로 범위가 명확하고 분량이 있는 코딩 작업을 프롬프트 하나로 autopilot 모드에 맡기는 경우를 권한다. 여러 번 주고받는 긴 대화형 세션의 성능은 다음 개선 대상이라고 밝혔다. 짧은 질문보다 한 번에 맡길 수 있는 구현 과제로 시험하는 편이 차이를 보기 쉽다.

써 본 결과는 Copilot CLI의 /feedback이나 GitHub Community 토론으로 보낼 수 있다. GitHub는 이번 프리뷰가 어떤 작업에 복합 워크플로가 도움이 되는지, 실제 사용에서 지연과 비용이 어떻게 달라지는지 배우기 위한 것이라고 밝혔다. 결과, 모델, 워크플로, 이름까지 바뀔 수 있다는 점도 미리 알고 쓰는 편이 좋다.

HydraFusion과 Auto 모델 선택은 무엇이 다른가

Copilot에는 이미 Auto 모델 선택이 있다. 작업을 보고 가장 잘 맞는 모델 하나를 골라 주는 기능이다. 이름만 보면 HydraFusion과 비슷해 보이지만, GitHub는 둘의 차이를 분명히 구분했다.

Auto는 요청마다 모델을 하나 고른다. HydraFusion은 실행 방식을 고르고, 한 번의 요청 안에서 여러 모델을 함께 조율한다. 초안은 한 모델이, 검토는 다른 모델이, 필요하면 승격은 또 다른 모델이 맡을 수 있다는 점이 다르다.

그래서 비용과 응답 시간도 다르게 봐야 한다. Auto는 모델 하나를 고르는 것이라 예측하기 쉽지만, HydraFusion은 Cascade로 승격되거나 Critique로 검토가 붙으면 한 요청에 여러 번의 모델 호출이 생긴다. GitHub는 내부적으로 각 단계의 역할, 결과, 비용, 지연을 기록한다고 밝혔지만, 사용자 요금이 어떻게 계산되는지는 발표에 나오지 않았다.

GitHub는 HydraFusion을 로컬, 클라우드, 복합 모델 사이를 자동으로 오가는 라우팅 전략의 한 부분으로 설명한다. 새 모델이 Copilot에 들어오면 평가를 거쳐 HydraFusion의 모델 풀에 넣을 수 있다고 했다. 모델 목록을 계속 바꿔 가며 고르는 대신 런타임이 조합을 맡는 방향이다.

HydraFusion 성능: Opus 5 대비 비용 36~67% 절감, 어떻게 쟀나

GitHub는 연구 글에서 세 개의 코딩 에이전트 벤치마크로 HydraFusion을 평가했다. 터미널 환경의 여러 단계 작업을 재는 TerminalBench 2.1, 큰 저장소의 실제 수정 작업을 재는 DeepSWE, 실제 Copilot 세션으로 만든 내부 벤치마크 CheckpointBench다. 비교 기준은 Claude Opus 5와 GPT-5.6 Sol이었다.

가장 좋은 설정 기준으로 Opus 5와 비교하면 TerminalBench 2.1에서 비용은 67% 낮고 검증된 작업 품질은 4.9점 높았다. DeepSWE에서는 비용 36% 낮고 품질 1.5점 낮았으며, CheckpointBench에서는 비용 65% 낮고 품질 0.1점 낮았다. 비용에는 초안, 비평, 수정, 승격, 재시도, 대체 호출까지 모두 포함한 추정 워크플로 비용을 썼다고 한다.

읽을 때 조건을 같이 봐야 한다. 모든 모델은 같은 medium 추론 수준으로 평가했고, 결과는 해당 벤치마크 판, 워크플로 설정, 모델 풀, 가격 가정에 한정된다고 GitHub가 직접 적었다. TerminalBench 2.1은 점수가 포화에 가까워 더 어려운 DeepSWE를 함께 봐야 한다는 설명도 있다. 어려운 저장소 작업에서는 품질이 Opus 5보다 약간 낮았다는 점이 중요하다.

정책을 만든 방식도 밝혔다. CheckpointBench는 실제 Copilot 코딩 세션을 공개 저장소의 고정된 커밋에 묶어 다시 돌릴 수 있게 만든 내부 평가다. GitHub는 임계값을 손으로 맞추는 대신 빔 서치로 결정 정책을 찾았고, 8월 11일에서 25일 사이 평가 도구 오류로 생긴 무효 실행은 추세에서 뺐다고 밝혔다. 내부 벤치마크가 포함된 만큼 외부에서 같은 결과를 확인하기는 어렵다.

결국 HydraFusion의 장점은 최고 점수보다 비용 대비 품질에 있다. 팀에서 시험한다면 같은 과제를 기존 모델과 HydraFusion으로 돌려 완료율, 응답 시간, 사용량을 함께 비교하고, 어떤 작업에서 Cascade나 Critique가 실제로 쓰였는지 진행 표시로 확인해 보는 것이 좋다.

자주 묻는 질문: Copilot HydraFusion

검색으로 많이 찾는 질문을 GitHub 공식 자료 기준으로 짧게 정리했다. 2026년 10월 29일 확인 기준이다.

HydraFusion은 어떤 요금제에서 쓸 수 있나요?

Copilot Pro, Pro+, Business, Enterprise 사용자가 쓸 수 있습니다. Business와 Enterprise는 관리자가 프리뷰 기능을 허용해야 합니다. 사용 시 요금이 어떻게 계산되는지는 발표에서 확인되지 않았습니다.

VS Code 모델 선택기에 HydraFusion이 안 보여요.

VS Code 1.140 이상 또는 Insiders인지 확인하고, 설정에서 chat.copilot.hydraFusion.enabled를 켭니다. 회사 계정이면 관리자가 프리뷰 기능을 허용했는지도 확인해야 합니다.

HydraFusion과 Auto는 무엇이 다른가요?

Auto는 요청마다 모델 하나를 고릅니다. HydraFusion은 실행 방식을 고르고 한 요청 안에서 초안, 검토, 승격에 여러 모델을 조율합니다.

HydraFusion이 Opus 5보다 좋은가요?

GitHub 자체 평가에서 비용은 36~67% 낮았지만 품질은 벤치마크에 따라 +4.9점에서 -1.5점까지 달랐습니다. 독립 재현 결과는 확인되지 않았습니다.
