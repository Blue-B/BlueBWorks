GitHub Copilot 컴퓨터 사용이란: API가 없는 앱을 화면으로 조작한다

회사에는 아직 API도 명령줄 도구도 없는 프로그램이 많다. 오래된 사내 경비 시스템, 설치형 회계 프로그램, 사람이 직접 클릭해야 하는 관리 화면 같은 것들이다. 에이전트가 코드는 잘 고쳐도 이런 프로그램 앞에서는 멈췄고, 결국 사람이 화면을 오가며 같은 입력을 반복했다.

GitHub는 2026년 10월 1일 Copilot CLI와 GitHub Copilot 앱의 macOS·Windows 버전에 컴퓨터 사용(computer use)을 공개 프리뷰로 추가했다. Copilot이 사용자를 대신해 데스크톱 앱의 내용을 읽고, 버튼을 누르고, 글자를 입력하고 고치고, 키를 누르고, 스크롤하고, 끌어다 놓고, 여러 앱을 오가며 작업 흐름을 진행할 수 있다.

GitHub는 이 기능으로 자동화 범위가 API, 명령줄 인터페이스, MCP 연동을 제공하지 않는 레거시·GUI 전용 소프트웨어까지 넓어진다고 설명한다. Changelog에 실린 시연 영상에서는 Copilot이 Safari에서 경비 보고서 작업 흐름을 따라가며 화면을 조작한다.

문서는 Copilot이 가능하면 백그라운드에서 앱과 상호작용해 사용자가 다른 앱에서 계속 일할 수 있다고 적었다. 앱 내용은 운영체제의 접근성 트리로 읽고, 시각적 맥락이 필요할 때만 스크린샷을 쓴다. 에이전트가 어떤 도구를 썼는지는 세션 기록에서 확인할 수 있다.

Copilot CLI와 앱에서 컴퓨터 사용 켜는 법

컴퓨터 사용은 기본으로 꺼져 있어서 직접 켜야 에이전트가 도구를 쓸 수 있다. Copilot CLI에서는 /computer on을 실행한다. /computer show로 현재 상태를 보고, /computer off로 끈다.

GitHub Copilot 앱에서는 설정에서 Computer Use를 열고 Enable Computer Use를 켠다. 앱의 입력창에서도 /computer on을 쓸 수 있다. 둘 중 어느 쪽에서 켜든 이후 요청에서 에이전트가 필요할 때 화면 조작 도구를 고른다.

macOS에서는 운영체제 권한 두 가지가 필요하다. 앱의 버튼과 입력란을 다루기 위한 손쉬운 사용(Accessibility) 권한과, 시각적 맥락이 필요할 때 창을 보기 위한 화면 기록(Screen Recording) 권한이다. Copilot이 처음 켤 때 이 권한을 주는 과정을 안내한다.

회사에서 관리하는 계정이라면 켜지지 않을 수 있다. 엔터프라이즈 관리자는 관리 설정으로 컴퓨터 사용을 끌 수 있고, 로컬에서 켜도 엔터프라이즈 정책을 덮어쓰지 못한다고 문서는 명시한다.

켜 둔 뒤에도 매 요청에서 화면을 조작하는 것은 아니다. 문서에 따르면 에이전트가 프롬프트를 처리하면서 필요할 때 컴퓨터 사용 도구를 고르고, 어떤 도구를 어떻게 썼는지는 세션의 도구 활동에서 다시 볼 수 있다. 처음 몇 번은 이 기록을 열어 어떤 창을 읽고 어디를 눌렀는지 확인해 두면 나중에 결과가 이상할 때 원인을 찾기 쉽다.

앱별 승인과 Always allow: 어디까지 허용할지 정하기

컴퓨터 사용은 세션이 돌아가는 Copilot 화면의 도구 권한 설정을 따른다. 이 설정에 따라 Copilot이 데스크톱 앱을 조작하기 전에 승인을 묻는다. 승인 요청이 뜨면 이번 세션에만 허용하거나, 다음 세션에도 쓰도록 저장하거나, 거부할 수 있다.

여기서 놓치기 쉬운 점이 있다. 승인을 물을지는 컴퓨터 사용 자체가 아니라 그 화면의 도구 권한 설정이 정한다. 문서는 이 설정을 화면마다 바꿀 수 있다고 적었다. 평소 CLI에서 도구를 넓게 자동 허용해 쓰고 있다면, 컴퓨터 사용을 켜기 전에 그 설정이 앱 조작까지 묻지 않고 넘기는지 먼저 확인하는 편이 안전하다.

Always allow를 고르면 그 결정이 컴퓨터에 로컬로 저장되고, 같은 컴퓨터의 Copilot CLI와 Copilot 앱 양쪽에 적용된다. 앱에서 항상 허용한 앱 목록을 보고 하나씩 지울 수 있다. 다만 지워도 이미 실행 중인 세션에 준 권한은 회수되지 않고, 다음 세션부터 적용된다.

거부 규칙은 자동 승인이나 저장된 승인보다 항상 우선한다. 특정 앱을 절대 건드리지 않게 하고 싶다면 거부 규칙을 두는 편이 확실하다.

GitHub 문서는 민감한 정보가 있거나 영향이 큰 동작을 할 수 있는 앱에는 Always allow를 쓰지 말라고 권한다. 한 번 항상 허용하면 이후의 컴퓨터 사용 동작이 다시 묻지 않고 그 앱을 조작할 수 있기 때문이다. 처음에는 세션 단위로 허용하고, 같은 작업을 여러 번 검증한 앱만 저장하는 순서가 안전하다.

하나 더 기억할 점은 저장된 승인이 도구를 가리지 않는다는 것이다. 앱에서 Always allow를 주면 같은 컴퓨터의 CLI 세션도 그 앱을 다시 묻지 않고 조작할 수 있다. CLI를 스크립트나 자동화에 묶어 쓰는 컴퓨터라면, 앱에서 허용한 목록을 주기적으로 확인해 필요 없는 항목을 지우는 편이 좋다.

선택적용 범위주의할 점
이번 세션만 허용현재 세션세션이 끝나면 다시 물음
저장 (Always allow)같은 컴퓨터의 CLI와 앱, 이후 세션이후 조작은 다시 묻지 않음, 앱에서 목록 확인·삭제

컴퓨터 사용이 맞는 작업과 알려진 실패 유형

문서가 예로 든 작업은 레거시 데스크톱 앱의 정보를 검토하고 요약하기, 프레젠테이션 내용 고치기, GUI 전용 소프트웨어에 정보를 입력하거나 수정하기, 여러 단계 작업에서 앱 사이로 정보를 옮기기다. Changelog는 브라우저 알림 요약이나 데스크톱 앱 작업 흐름 진행도 예로 들었다.

GitHub는 원하는 결과, 관련된 앱, 중요한 제약을 함께 설명할 때 가장 잘 동작한다고 안내한다. 예를 들어 '경비 시스템에서 이번 달 미제출 항목만 찾아 목록으로 정리하고, 제출 버튼은 누르지 말 것'처럼 범위와 금지 동작을 같이 적는 식이다. 이 문장은 BlueBWorks가 만든 예시다.

한계도 문서에 분명히 적혀 있다. 컴퓨터 사용은 앱 버전, 운영체제, 창 상태에 따라 바뀌는 화면을 해석한다. 그래서 잘못된 컨트롤을 고르거나, 엉뚱한 곳에 글자를 넣거나, 비표준·동적 컨트롤과 복잡한 흐름에서 어려움을 겪을 수 있다. 타이밍이나 창 상태가 달라지면 결과가 바뀌고, 같은 동작을 반복하거나 진행을 멈출 수도 있다.

그래서 API, CLI, MCP 같은 통합 수단이 있는 도구라면 그쪽을 먼저 쓰는 편이 안정적이다. 컴퓨터 사용은 그런 수단이 없을 때의 대안으로 두고, 되돌릴 수 있는 반복 작업부터 시작해 결과를 확인하며 넓혀 가는 것이 좋다.

BlueBWorks가 제안하는 시험 순서는 이렇다. 먼저 화면을 읽고 요약만 하는 작업으로 시작해 에이전트가 화면을 제대로 읽는지 본다. 다음으로 테스트 데이터에 입력하는 작업을 세션 승인으로 돌리고, 도구 활동 기록과 결과를 대조한다. 같은 작업이 여러 번 안정적으로 끝난 뒤에야 실제 데이터와 저장 승인으로 넘어가는 것이다. 이 순서는 문서가 밝힌 실패 유형을 바탕으로 한 편집부 제안이며 GitHub의 공식 절차는 아니다.

창 상태가 결과를 바꿀 수 있다는 점도 실무에서 중요하다. 작업할 앱을 미리 열어 두고, 팝업이나 업데이트 알림처럼 화면을 가리는 요소를 정리해 두면 에이전트가 엉뚱한 컨트롤을 고를 가능성이 줄어든다. 앱을 업데이트해 화면 배치가 바뀌었다면 이전에 잘 되던 작업도 다시 확인해야 한다.

보안과 개인정보: 화면에 보이는 것은 모두 맥락이 된다

컴퓨터 사용은 화면에 보이는 내용을 읽는다. 앱 창에는 민감한 정보나 다른 사람에 관한 정보가 보일 수 있다. GitHub 문서는 화면에 보이는 내용을 Copilot에 맥락으로 넘겨도 괜찮은 앱과 작업에만 이 기능을 쓰라고 권한다.

작업을 시작하기 전에 관련 없는 창을 닫고, 고객 정보나 인사 정보처럼 노출되면 안 되는 화면이 함께 열려 있지 않은지 확인하는 습관이 필요하다. macOS의 화면 기록 권한은 시각적 맥락이 필요할 때 창을 보기 위한 것이므로, 어떤 창이 보이는지가 곧 무엇이 전달되는지를 정한다.

실행 중 예상과 다르게 움직이면 바로 멈춘다. Copilot CLI에서는 Esc를 두 번 누르고, Copilot 앱에서는 Stop을 누르거나 Esc를 누른다. 책임 있는 사용에 관한 더 자세한 내용은 GitHub의 Copilot 에이전트 애플리케이션 카드에 정리돼 있다.

조직에서 도입한다면 관리자가 먼저 정책을 정하는 편이 좋다. 엔터프라이즈 관리 설정으로 기능 자체를 끌 수 있으므로, 허용할 팀과 용도를 정한 뒤 켜고 Always allow 사용 기준을 함께 안내한다. 기능은 기본으로 꺼져 있어, 정책으로 막지 않아도 사용자가 직접 켜기 전에는 화면 조작이 일어나지 않는다.

자주 묻는 질문: Copilot 컴퓨터 사용

검색으로 많이 찾는 질문을 GitHub 공식 자료 기준으로 짧게 정리했다. 2026년 10월 29일 확인 기준이다.

Copilot 컴퓨터 사용은 어디서 쓸 수 있나요?

Copilot CLI와 GitHub Copilot 앱의 macOS·Windows 버전에서 공개 프리뷰로 쓸 수 있습니다. 기본은 꺼져 있어 직접 켜야 합니다.

어떻게 켜고 끄나요?

CLI에서는 /computer on으로 켜고 /computer off로 끕니다. 앱에서는 설정의 Computer Use에서 Enable Computer Use를 켭니다. 실행 중에는 CLI에서 Esc 두 번, 앱에서 Stop이나 Esc로 멈춥니다.

Copilot이 허락 없이 앱을 조작하나요?

도구 권한 설정에 따라 앱을 조작하기 전에 승인을 묻습니다. 다만 Always allow를 고른 앱은 이후 다시 묻지 않으므로 민감한 앱에는 쓰지 않는 것이 좋습니다.

회사 계정에서 켜지지 않아요.

엔터프라이즈 관리자가 관리 설정으로 기능을 끈 경우 로컬에서 켤 수 없습니다. 관리자에게 정책을 확인해야 합니다.
